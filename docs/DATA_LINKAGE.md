# RED-2400 Data Linkage -- Complete Arithmetic

This document contains the full data-linkage arithmetic that the
JOSS paper summarises in the "Data linkage" section. It is
regenerated by running
`red2400_toolkit.audit_runner.run_audit(deposit_dir, on_missing='quarantine')`
against the RED-2400 v2 deposit (Zenodo concept
[@kamat2026red2400]).

## Registry-side partition (rejections)

| Quantity | Count |
|---|---:|
| Registry rejection events (total) | 6,660 |
| Registry events linked to at least one outcome row (`n_linked_registry_events`) | 3,333 |
| Orphan registry events (no attachable outcome) (`n_orphan_rejections`) | 3,327 |

Identity: `3,333 + 3,327 = 6,660`.

## Outcome-side partition (`event_id` collapse)

| Quantity | Count |
|---|---:|
| Outcome rows total | 169,123 |
| Outcome rows with missing/malformed `rejectTs` or `rejectReason` (`n_orphan_outcomes`, row-level) | 348 |
| Distinct outcome-side `event_id` values (`n_distinct_outcome_event_ids`) | 3,878 |
| Outcome-side `event_id` values that DO match a registry event | 3,333 |
| Outcome-side `event_id` values that do NOT match any registry event (`n_orphan_outcome_event_ids`) | 545 |

Identity: `3,333 + 545 = 3,878`.

## Reading the two numbers together

- `3,333` is the SCIENTIFIC denominator for per-filter shares and
  save-to-miss ratios. It counts registry rejection events with at
  least one attachable outcome row.
- `3,878` is the outcome-side identifier count. It is larger than
  `3,333` because some outcome rows carry `event_id` values that
  the registry side does not recognise (after timestamp and reason
  normalisation). Those 545 unmatched identifiers are surfaced by
  `n_orphan_outcome_event_ids`; the toolkit refuses to silently
  attach them to any registry event.

## Downstream classifiability

- 43.83 % of registry events fall to the `unclassifiable` tier
  because they have no in-window forward sample or terminal
  lifecycle transition to key against. Per-filter counts of
  included events are always reported in `AuditResult.filter_counts`
  so any downstream share is auditable.

## Filters with small n

Filter `filter_8` has n = 19 in the v2 deposit. Per-filter
percentages for that filter are unstable; downstream inference
should use cluster-robust methods over repeated mints
[@cameron2015practitioner]. The toolkit reports raw frequencies
without confidence intervals.
