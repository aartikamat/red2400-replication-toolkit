# Contributing to RED-2400 Replication Toolkit

Thank you for considering a contribution. This project exists to make
outcome-classified filter auditing on the RED-2400 benchmark reproducible
and scientifically defensible. Corrections, additional adapters, and
independent oracles are all welcome.

## Ways to contribute

- **Report a defect** — open a GitHub issue with a minimal reproducer
  (source excerpt or a hand-constructed fixture). Scientific-correctness
  bugs are treated as top priority (see the `scientific-correctness`
  label).
- **Add or strengthen tests** — adversarial fixtures for edge cases you
  encounter are especially valuable. Any new fixture must ship with
  hand-computed expected outputs, not fixtures generated by the
  production code.
- **Improve documentation** — corrections, tutorials, or clarifying
  examples are welcome via pull request.
- **Add a dataset adapter** — the toolkit is being generalized to support
  more than the RED-2400 deposit. Adapter proposals should follow the
  event-linkage contract described in `red2400_toolkit/event_model.py`.

## Ground rules

1. **No silent aggregation.** Any code path that pools rows across
   distinct rejection events must be explicit about the estimand and
   never used as a hidden substitute for another mode.
2. **Independent oracles first.** Tests may not compare production
   output against fixtures generated by the same production code. Use
   hand-worked tables or an independent implementation (see
   `tests/oracle.py`).
3. **Preserve the audit trail.** Do not rewrite git history on `main`.
   Do not delete or move tags — corrections are added as new tags, not
   in place of existing ones.
4. **Fail loudly.** New parsers and validators must surface schema drift
   as an exception or quarantine record; silent fall-through is a bug.

## Development workflow

1. Fork the repository and create a topic branch:
   ```
   git checkout -b fix/short-slug
   ```
2. Install in development mode:
   ```
   pip install -e ".[test,figures]"
   ```
3. Run the tests before pushing:
   ```
   pytest -v
   ```
   If your change adds an adversarial fixture, extend
   `ADVERSARIAL_HAND_TABLE` in `tests/conftest.py` with the hand-computed
   expected tier.
4. Open a pull request with:
   - A one-paragraph summary of the change and why it is needed.
   - A test-plan checklist (which fixtures exercise the change).
   - A link to the issue it closes, if any.

## Commit-message style

Short imperative subject line, wrapped body if needed:

```
Fix orphan-outcome pooling in adapter_x

Adapter X was silently mint-pooling outcome rows when the alias-schema
timestamp normalizer returned None. Route such rows to quarantine and
add a fixture covering the case.

Closes #42.
```

## Code style

- Python 3.10+; type hints on public functions.
- No new runtime dependencies without discussion — the core dispatch
  keeps to stdlib + `pandas`.
- Docstrings on every public function; reference the paper section or
  the P11 canonicalization spec where appropriate.
